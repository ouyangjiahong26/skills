# 性能优化

一套纪律：测量在先，改动在后，每一步用基准数字说话。没有基准数字不开工。跳过测量、凭直觉改代码是本 skill 的禁止项。

分工：性能回归（以前快、现在慢）走 `diagnosing-bugs` 阶段 4 的性能分支做诊断。本 skill 管主动优化，即用户要它更快、更省，而不是它坏了。

## 步骤

### 1. 建基准，定目标

写一个可重复执行的基准脚本：

- 固定输入：数据集与随机种子固定，噪声源（时间、网络、并发度）一并固定
- 预热：空跑若干轮，让 JIT、缓存、page cache 进入稳态后再计时
- 多次取中位数：同一配置跑多轮（轮数写进脚本），取中位数，不取单次最优

跑通后记下当前值（baseline），并把目标约定成数字（如 P95 从 120ms 降到 50ms、峰值内存从 2GB 降到 512MB）。用户只说“变快”没给数字：先报当前值，提出一个可检查的目标请用户确认。

本步产出：一条命令可重跑的基准脚本、当前值、数字化目标。

### 2. 用 profiler 定位热点

用 profiler 找热点，不猜：采样 profiler / 火焰图（CPU）、alloc profile（内存）、query plan / 慢查询日志（数据库）、trace（端到端延迟分布）。

产出排名前几的热点，各带占比。只优化测出来的热点。

### 3. 一次一个假设地改

每个优化动作对应一条瓶颈假设：“如果 X 是瓶颈，那么改 Y 会让指标 Z 改善。”改完用步骤 1 的同一基准重跑：

- 数字改善、行为测试全部通过：保留改动，更新基线数字，进入下一条假设
- 无改善或变差：回滚这个改动，换下一条假设

一次只改一个变量。多个优化攒在一起测，赢了输了都无法归因。

热点对照常见瓶颈模式排查：

- 算法复杂度：热路径上的嵌套循环、容器内线性查找，换算法或数据结构
- 重复计算：同一结果反复算，缓存（memoize）或提到循环外
- N+1 查询：循环里逐条查库，改为批量取回、join、预加载
- 热路径上的序列化：每个请求重复 JSON 解析、ORM 对象组装，缓存序列化结果、削减 payload
- 锁竞争：并行被临界区串行化，核跑不满，收窄临界区、分片锁、无锁结构
- 分配压力：热路径频繁分配，GC / realloc 停顿，复用缓冲区、对象池、消除中间集合

### 4. 验证

- 同一基准（同一脚本、同一数据、同一机器）对比前后数字
- 行为测试全部通过。开工前先确认测试本来就全部通过，之后的通过才是有效证据。性能改动不改行为

## 边界情况

| 情况 | 处理方式 |
|---|---|
| 基准噪声大到看不出改动效果 | 先收紧基准（加长运行、隔离 CPU、固定频率）。仍不行就报出方差，问用户是否接受当前分辨率 |
| 目标经测量证明不可达 | 停止改动。报告已排除的假设、剩余瓶颈的证据、可达的折中目标 |
| 数据集或环境无法固定（依赖线上流量、外部服务） | 说明缺口，问用户要可固定的工作负载样本。拿不到就不开工 |

## 完成条件

- [ ] 量化目标达成，或已用测量数据证明不可达并指出瓶颈
- [ ] 行为测试全部通过，无行为回归
- [ ] 报告含同一基准的前后数字，每条保留的优化都对应一条已验证的假设

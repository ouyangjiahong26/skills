# ADR 格式

ADR 放在 `docs/adr/`，用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

`docs/adr/` 目录按需创建：只在需要第一个 ADR 时才建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这样。一个 ADR 可以只有一段。价值在于记录*做了*一项决策以及*为什么*，不在于填满各节。

## 可选小节

只在真正增加价值时才加这些。大多数 ADR 用不着。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策被重新审视时有用
- **Considered Options**：只在被否决的替代方案值得记住时
- **Consequences**：只在需要点出不明显的下游影响时

## 编号

扫 `docs/adr/` 找到现有最大编号，加一。

## 何时提议 ADR

以下三条必须同时为真：

1. **难以撤销**：事后改变主意的成本很大
2. **缺乏上下文会令人困惑**：未来的读者看到代码会想"他们到底为什么这么做？"
3. **源于真正的权衡**：存在真实的替代方案，你因特定理由选了其中一个

如果一项决策容易撤销，跳过，改主意时直接改就是。如果不令人困惑，没人会问为什么。如果没有真正的替代方案，除了"我们做了显然的事"之外没什么可记的。

### 什么样的算数

- **架构形状。** "我们用 monorepo。""写模型是事件溯源的，读模型投影到 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，不是同步 HTTP。"
- **带锁定效应的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库，只是那些换掉要花一个季度的。
- **边界和范围决策。** "Customer 数据归 Customer 上下文拥有；其他上下文只按 ID 引用。"明确的"不"和明确的"是"一样有价值。
- **对显然路径的有意偏离。** "我们用手写 SQL 不用 ORM，因为 X。"任何理性读者会假设反面的东西。这些能阻止下一个工程师去"修"一个有意为之的东西。
- **代码中看不见的约束。** "因为合规要求我们不能用 AWS。""因为合作方 API 合同，响应时间必须在 200ms 以下。"
- **否决得不明显的替代方案。** 如果你考虑过 GraphQL，出于微妙的原因选了 REST，记下来，否则六个月后有人又会提 GraphQL。

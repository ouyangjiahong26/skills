你拿到了一份规格。这份规格应当带有关联的工单，描述如何实现这份规格。

目标是在单个分支上交出一个实现整份规格的 PR。

工单不是步骤清单，而是一张带阻塞关系的**任务图**。所以总有若干就绪工单构成**前沿（frontier）**，可以随时认领。

与子代理的往来通信保持克制。主要靠**上下文指针（context pointer）**沟通：指向规格、工单、研究笔记和此前的提交。指针已经提供的信息不要复述。

**实现子代理（implementer subagent）**尽可能在后台运行，争取**最大并发**。

## 步骤

1. 读规格和工单，读到理解任务图为止。

2. （可选）用一个**探索子代理**完成工单要求的探索：相关代码库文件或外部文档。确保探索子代理能保存文件：它应把 markdown 笔记存到仓库之外、所有后续子代理都能访问的目录里。这让**实现子代理**专注于实现，不用分心探索。

3. 建分支，开草稿 PR。标题以 `[AI Generated][<类型>]` 开头，正文标记为 'closing' 规格 issue 和各工单。

4. 用**实现子代理**逐张实现工单。每个实现子代理在各自的工作树（worktree）、各自的分支上干活。

5. 某个**实现子代理**完成后，用**合并子代理（merger subagent）**把它的成果并进 PR 分支。

6. 若这改变了可认领工单的**前沿**，接着派更多**实现子代理**处理新工单，保持最大并发。

7. 全部工单完成后，对 PR 分支调用 Skill 工具，传入 "code-review"。把它提出的问题交给单个**实现子代理**一次修完。

8. 把 PR 标记为 ready for review。

9. 清理所有**实现子代理**的工作树。

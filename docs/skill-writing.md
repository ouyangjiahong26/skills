# Skill 写作规范

SKILL.md 是 agent 在编码过程中**被触发的行为指令**，不是一次性任务 prompt。写好 skill 的核心是讲清三件事：**做什么、边界在哪、什么时候停下来问**。角色设定和思考指导对 agent 行为影响极小，skill 应专注于明确的行为指令。

**可预测性**是 skill 设计的根美德——agent 每次运行走同一个*过程*（不一定是同一个产出）。写每一行时都该问：这能不能让 agent 行为更可预测？

## 和任务 prompt 的区别

常说的“好 prompt”五要素（Context / Request / Output Format / Constraints / Checkpoint）针对的是**给模型分配一次性任务**。Skill 是长期挂载、等调用的规范，Context 和 Output Format 每次调用都不同，写死进 SKILL.md 是错的。映射如下：

| 任务 prompt 要素 | 在 skill 里怎么处理 |
|---|---|
| Context | 模型可调用 skill 的 `description`：写触发场景；手动 skill 的 `description`：写给用户的一行用途说明。正文不写调用时才有的背景 |
| Request | 正文开头：写明核心行为（具体做什么动作） |
| Output Format | 正文单独章节：只在 skill 有固定产出时写（如 commit message 格式、交接文档结构） |
| Constraints | 正文章节：边界情况表 + 明确的“不要做什么” |
| Checkpoint | 正文章节：写明什么时候停下来问用户、什么时候自己继续 |

## frontmatter：调用边界

先决定 skill 的调用方式：

- **模型可调用**：省去 `disable-model-invocation`。`description` 是常驻的模型上下文指针，写清用途和触发场景；适合模型或其他 skill 必须自行发现的流程。
- **只允许手动调用**：设 `disable-model-invocation: true`。用户显式输入 `/skill-name` 才会运行，`description` 改为人类可读的一行用途说明；适合提交、推送、部署、外部写入等需要用户授权的流程，以及会直接或间接调用自身的递归流程。

调用其他 skill 本身不是手动限制的理由：需要模型在任务中自动编排的 skill 可以保持模型可调用。

```yaml
---
name: <skill-name>                   # 目录名，也是命令名（/<skill-name>）
description: <一句话用途或触发场景>
argument-hint: "可选的参数提示"
disable-model-invocation: true      # 仅手动调用时设置
---
```

- **`name`** 命令名直接由它来（`<name>` → `/<name>`）。
- **`description`**：模型可调用时，写做什么和何时触发；仅手动调用时，删掉触发词和内部流程，保留用户理解命令用途所需的一句话。
- **`argument-hint`**（可选）：参数提示，告诉用户调用时可以传什么。
- **`disable-model-invocation`**（可选）：设为 `true` 后只有用户能显式发起，模型与其他 skill 都不能调用。
- **信息边界**：description 不暴露内部步骤或 references 摘要；正文才服务执行。

## 正文：按需写这几节

不是每节都要。按 skill 的复杂度挑着写。

### 核心行为

开头一段话或几行祈使句，说清这个 skill 执行什么动作。极简的 skill 整个正文就是核心行为，十几行讲清楚就够了：

> 就这个计划的每个方面对我进行不间断的追问，直到达成共识。……一次只问一个问题，等拿到反馈再继续。如果一个问题可以通过探索代码库来回答，就去探索代码库，不要问用户。

这个例子用祈使句直接说明了交互方式和探索优先级。

### 步骤 / 工作流（有明确流程时）

有明确流程的 skill 分步骤写，每步是**可检查的**动作。典型如分四步走（分析起草 → 确认执行 → 验证 → 收尾），关键步骤结尾写明该步骤的输出。

### 边界情况（涉及外部依赖时）

skill 涉及文件、git、网络、用户输入时，用表格列**情况 → 处理方式**。从异常输入、外部依赖失败、状态不一致三个维度梳理。这是 skill 里最实用的一节——agent 遇到意外时照表办事，而不是自己猜。范例：

| 情况 | 处理方式 |
|---|---|
| 没有会话文件被改动 | 不提交，告知用户 |
| 会话文件存在合并冲突 | 不提交，先解决冲突 |

每个 skill 有隐含假设（运行环境、依赖文件、项目结构）。在边界情况表中，把假设失效的情况**单独标注**，和运行时异常区分开。假设失效时的处理通常是"告诉用户环境不满足前置条件"，不是尝试继续执行。

### Checkpoint（何时暂停）

写明哪些地方**必须停下来等用户**，哪些**自己做完整再说**。涉及不可逆操作的 skill 要写死“绝不自行执行”；纯确定性、无副作用的脚本型 skill 不用停。

只有三种情况该暂停：

1. 涉及不可逆操作（提交、推送、删除、关闭 issue）
2. 任务范围发生变化（用户要的东西和最初不一样了）
3. 需要用户提供信息才能继续

其他情况自己做完再汇报。

### 输出格式（有固定产出时）

skill 的产出有固定格式要求时，明确规定格式。如 commit message 的结构、交接文档的章节、API 响应的 schema。没有固定产出的 skill 不需要这一节。

### 完成条件（有明确终点时）

做成什么样算完成，逐条列出。完成条件有两个维度：

- **清晰度**：agent 能分辨 done 和 not-done 吗？含糊的完成条件（如"达成共识"）招致**过早结束**——agent 会跳过剩余工作直接宣布完成。
- **要求度**：要求多彻底？"列出每条改动"比"列几条改动"要求度高。这个维度不限于步骤——纯参考型 skill 也能通过"每条规则都应用了"来设定彻底性要求。

最强的完成条件同时满足两者：可检查且彻底。没有明确终点的 skill（交互式、纪律型）不要硬加——它们本来就没有终点。

## 失败模式

用这些诊断 skill 的问题：

- **过早结束**——步骤没做完就跳到下一步，agent 的注意力滑向"做完了"而非"做着"。首先收紧完成条件；只有完成条件天然含糊且确实观察到跳过行为时，才通过拆分来藏后续步骤。
- **重复**——同一个意思出现在多处。花维护成本、花 token，还把一个意思的显眼度抬过了它该有的层级。
- **沉积**——过时内容堆积，因为加觉得安全、删觉得危险。没有修剪纪律的 skill 的默认命运。
- **膨胀**——skill 太长，即使每行都有用。靠信息层级治：把参考挪到外部文件，按分支或顺序拆分。
- **空操作**——模型默认就会做的事，说了白说。测试：删掉后行为有区别吗？弱引导词（如"要彻底"）比强引导词（如"relentless"）更容易变成空操作。
- **否定**——通过禁止来引导行为往往适得其反——"别想大象"反而让大象更突出。用正面描述替代禁止。只在无法正面表述时保留否定，且同时给出正面目标。

## 不该写的

- **角色设定**（“你是一个资深工程师，擅长……”）。agent 的能力由底层模型决定。
- **教 agent 怎么思考**（“以批判性思维审视”“仔细想想”）。这类指令不改变行为输出。写“做什么”和“边界在哪”，不写“用什么心态”。
- **死的 Context / Output**。调用时才有的背景，别写进 SKILL.md。
- **为完整而注水**。没有边界情况就别编边界情况表，没有参数就别写 `argument-hint`。

## 中文统一用词

直接从英文术语机翻过来的词容易漂移，以下是既定约定（同一概念只用一个词，不另造同义词）：

- **接口**（interface / seam）：两个部分相接、可独立变化的边界。不说**接缝/缝/seam**，也不说**边界**（与 DDD 的限界上下文撞了）。
- **调用方**（caller）：使用本库/本模块的下游程序或人。不说**消费方/消费者/consumer**；作动词时说**调用**或**使用**，不说**消费**。
- **术语表 / 术语清单**（glossary / closed value set）：不说**词汇表/词表/vocabulary**。
- **调用链**（call chain）：调用方调起本库的路径。不说**通道/channel**。
- **契约**只指有约束力的约定（agent brief、行为契约、共享契约）；随版本冻结的保证直接说**版本**（如“包版本即术语版本”），不说“词表契约”。

## 信息层级

Skill 的内容按 agent 需要的紧迫度分三层：

1. **正文中必须执行的动作**（步骤）—— agent 一触发就要做的事，是 SKILL.md 的主层。每步结尾带一个可检查的完成条件。
2. **正文中按需查阅的参考**（规则、定义、事实）—— agent 在执行中遇到疑问时查阅。纯参考型 skill（如 review checklist）整个正文都是这层。
3. **外部文件中的参考**（通过 context pointer 按需加载）—— 从 SKILL.md 里分出去的独立文件，只有 agent 实际需要时才加载。

把参考从正文挪到外部文件，就是**渐进式披露**——顶层保持可读，详情按需加载。分出去的文件放在 skill 目录下，通过 markdown 链接指向。

**分支**（skill 的不同调用路径）是渐进式披露的关键判据：每个分支都需要的内容 inline，只有部分分支需要的放在外部文件。

## 长度

短的 skill 十行以内，长的近百行，都合理。判断标准不是行数，是**每一段是否改变了模型的行为**：

> 删掉这一段后，agent 会做出不同的事吗？不会，就删掉。

## 引导词

**引导词**是一个模型预训练中已有的紧凑概念，反复出现在 skill 文本中，利用模型已有的先验知识来锚定行为。如 "red" 锚定了 TDD 的循环状态，"tracer bullets" 锚定了垂直切片。

引导词有双重作用：
- 在正文里锚定**执行**——agent 看到同一个词就调用同一套行为。
- 在 description 里锚定**触发**——当 prompt、文档、代码里用同一个词时，agent 更容易触发该 skill。

找现成的词，别自造。自造的词没有先验可借，你得花定义 token 去解释它本该免费给你的东西。

## 何时拆分 skill

每拆出一个新 skill 都要花代价（要么花 context load，要么花 cognitive load），只在值得时拆：

- **按调用方式拆**：当你有一个独立的引导词应该单独触发时，拆出 model-invoked skill——花 context load 换独立触发。
- **按执行顺序拆**：当后面的步骤会诱惑 agent 跳过当前步骤（过早结束）时，把后续步骤藏到另一个 skill 里。

## 修剪

每条语句都该过一遍修剪：

1. **单一来源**——每个意思只放一处。改行为只需改一处。
2. **相关性**——每行是否还跟 skill 的行为相关？
3. **空操作测试**——逐句审查："删掉这句后 agent 行为有区别吗？"没区别就删。删整句，不修字。大部分通不过测试的散文该删，不该重写。

## 好 skill 的特征

- **简洁**——每句都改变 agent 行为（删掉后行为有区别吗？）
- **可维护**——易变部分（边界情况表、完成条件）和稳定部分（核心行为）物理分离
- **有约束**——主动设定范围限制（限定改什么文件、限定多长时间、限定什么不碰），避免 agent 过度投入
- **可组合**——与其他 skill 通过"下一步"形成清晰的链式关系

## 起步
